## End-to-end dataflow

1. **Publisher API → fetcher.** `updater/strategies/fetchers/<source_id>.py`, invoked by its strategy via `strat.run(unit, since=sane_since(...))` — the corrupt-far-future-cursor guard is applied at the hand-off, not per fetcher (orchestrate.py:866-884; measured: 28/93 units carried a future frontier, only 4 of 12 guarded it).
2. **Fetcher → merge.** New rows go through `merge.merge_and_write`: union + dedup (`series_key`,`obs_date`; new wins) + never-shrink check + atomic publish (merge.py:1-19).
3. **Parquet store.** `data/clean_full/<src>/*.parquet` via `blob.write_table_atomic` (blob.py:159-199). Under `AQUEDUCT_BACKEND=r2` the four path primitives translate the path to key = everything after the last `/data/` segment (blob.py:59-69) and publish to `r2://econ-data/clean_full/<src>/...`; **R2 is the source of truth in CI, and the local file is kept as scratch mirror for the same-run CSV derive** (blob.py:42-48, 194-199). `open()`/raw `pq.read_table(path)`/`os.listdir` are forbidden in fetchers: on a CI runner the local path does not exist, so a raw read silently ingests nothing (R36; blob.py:85-87, 125-128, 202-211, 249-253).
4. **Derive CSVs (same run, contract step 5 / §5.7).** `orchestrate._derive_changed_csvs` takes the changed set from `res.series_cursors` and NOTHING else (orchestrate.py:285-293); `_catalog_ids_for` maps store keys → catalog ids (exact, flow-grain PxWeb fallback, punctuation-insensitive fallback; orchestrate.py:505-605); `derive.derive_and_put` PUTs `series/<urlenc>.csv` to R2. Failures land in `csv_retry_queue` (state.py:149-155) and demote the run to `partial` — the parquet publish is never rolled back (orchestrate.py:892-900).
5. **catalog.db.** CI pulls it from `r2://econ-data/_aqueduct/catalog.db.zst` each run (updater-daily.yml:161-176, streamed in updater-heavy.yml:185-205); derived ids are appended to `data/_aqueduct/pending_catalog_sync.txt` (orchestrate.py:263-282, 381).
6. **D1 (`econ-catalog`).** Post-run: `core/sync_state_d1.py` (freshness) then `core/sync_catalog_d1.py` (new series rows), both executed as `npx wrangler d1 execute econ-catalog --remote --file=...` from `api/worker` with the version-pinned wrangler (sync_state_d1.py:20-26).
7. **Worker.** `api/worker/` serves `/v1/catalog`, `/v1/last-updates`, metadata from D1 and `/v1/series/{id}.csv` via R2 GET; a source not in `SUPPORTED_SOURCES` (util.ts:19) answers 501.
8. **Deploy — MANUAL ONLY.** `cd api/worker && wrangler deploy` (api/DEPLOY.md:46-53; `npm run deploy` in api/worker/package.json:10) → live `econdl-api` worker. **Nothing in `.github/workflows/` deploys the worker** — verified by grep: the only workflow `deploy` match is `pages deploy catalog/site` in deploy-site.yml:62, which is the STATIC SITE, not the worker. Pushing worker code publishes nothing until someone runs wrangler by hand.

## State semantics (the part everyone gets wrong)

**Which statuses write what** (orchestrate.py:885-928):
- `ok` / earned `no_change` → `upsert_unit` WITH `last_success_utc=now` and vintage advanced (`res.new_vintage or vintage`); `upsert_source(status="ok", last_success_utc=now)` (orchestrate.py:907-925). An **earned** no_change (probe token == stored vintage) is recorded too, so a quiet healthy source doesn't rot into RED-SLA; an UNDETERMINABLE probe records nothing — laundering it into no_change is what §5.2 forbids (orchestrate.py:830-853).
- `partial` → `last_success_utc` is **NEVER set** (`ok` is False → keeps old value, orchestrate.py:916), vintage is **NOT advanced** (orchestrate.py:909-912, so the next run re-checks + re-derives), and **`upsert_source` is not called at all** — a permanently-partial source has NO `source_state` row (health.py:186-190, R231). `series_cursors` ARE still stored on a csv-partial: those rows genuinely published (§5.1, orchestrate.py:918-922).
- `transient_fail` (TransientError, `UnitTimeout`, or any unexpected Exception) → `_record()`: unit status + `last_attempt_utc` + clipped `last_error` only (orchestrate.py:929-944, 1037-1040; `_clip_err` bounds at 1,400 chars and announces truncation, orchestrate.py:91-118).
- `DefinitiveError` is recorded as status **`partial`** (orchestrate.py:939-941).
- `runs` log row is written for every outcome; `obs_count` in `unit_state` is **NOT comparable across runs** — 13 fetchers fall back to total-store row count on a zero-write run; ecb "lost" 168M obs in 3 days while the store gained 23 rows (state.py:23-50, R326). To size a source, count the store.

**Tally taxonomy** (_common.py:173-234, 262-292): `added_unit`/`empty_unit` (attempted), `transient_unit` (attempted+failed, retry may help), `structural_unit` (200-but-parsed-0-rows — `finalize()` raises DefinitiveError naming offenders), `deferred_unit` (**not attempted, not a failure** — budget stopped the sweep; counting deferrals as transient made ecb read "252/540 transient-failed" when nothing failed, R303). finalize order: structural → DefinitiveError; all-empty over a >10-sub-unit window → DefinitiveError; any transient → `partial`; any deferred → `partial` (honest: coverage incomplete, vintage must not advance); else `ok`(added>0)/`no_change`. Every budgeted fetcher MUST rotate (`load_rotation`/`save_rotation`/`rotate_after`) or have a per-sub-unit freshness sidecar — a bound over a stable order re-walks the same prefix forever, a self-certifying outage (R190, _common.py:92-99, 534-548).

**The two state lineages.** `state.db` is a single whole file. CI's authoritative copy is `r2://econ-data/_aqueduct/state.db.zst`, round-tripped by `--pull-state` (records ETag, re-HEADs after GET to catch mid-download movers, run.py:67-106) and `--push-state` (VACUUM INTO + zstd-9 + compare-and-swap; exit 2 = another writer won, state NOT overwritten; dated backup under `_aqueduct/backups/`, run.py:109-180). There is **no row-level merge anywhere**: a pull wholesale-replaces the local file (run.py:92-96) and a push wholesale-replaces the remote. So the workstation's `data/_aqueduct/state.db` and the R2 object are *lineages*, not copies — any state written locally outside a pull→push cycle (e.g. a bare `python -m updater.run --source X`) exists only in the local lineage and is destroyed by the next pull; the CAS turns a lost race into a loud refusal, never a reconciliation. `run_local_heavy.ps1` joins the R2 lineage by wrapping its pass in pull/push and refusing to overlap CI (R5, run_local_heavy.ps1:143-157, 214-235). The health gate reads whichever store is in front of it: the CLOUD gate therefore declines to judge `run_location: local` sources (their rows there are stale-by-construction — noaa was red-flagged daily for this until nobody read the gate at all, R244; health.py:347-361) but still watches for a whole ROUTE going silent ≥3 days (health.py:398-455).

**A state row is a snapshot of the last RUN, not current truth.** Because `partial` never sets `last_success_utc`, the ATTENTION column shows whenever the source last ran — measured 2026-08-02: of 54 partial sources, 24 hadn't been *attempted* for 2+ days (oldest 39 days) because the daily run reaches ~20 of ~106 cloud sources within its budget (health.py:175-183, R231/R246). Three sources chased that day (cso, insee_melodi, imf_*_direct) were healthy upstream with a stale verdict. `last_attempt_age_d` exists precisely to expose this (health.py:191-194).

**Health verdicts** (health.py): `ATTENTION_STATUSES = ("partial","definitive_fail","transient_fail","running")` (health.py:28). Order of judgement: no state at all → RED-UNRUN if adapter built else PENDING; any attention unit → ATTENTION; never succeeded → RED-UNRUN; `succ_age > cadence×2.0` → RED-SLA; newest *observed* (not forward-dated — projections to 2071 masked staleness on 28/93 units) obs older than the data clock → RED-DATA unless a fresh `upstream_verified` dict claim covers it (claims expire after 180 days) (health.py:239-299). Daily sources age in business days (Monday false-red fix, health.py:78-115). Irregular publishers get a 365-day lateness clock; `data_cadence` (measured, never guessed) can decouple the lateness clock from the polling cadence (health.py:128-166).
