## Rules (from R-entries lines 1–3300 of MISTAKES.md)

### Registry & scheduling
- `updater/registry.yaml` + `EXPECTED_SOURCE_COUNT` in `updater/config.py` are ONE atomic change; a mismatch or an unparseable registry makes `orchestrate.run_once()` raise SystemExit and takes ALL sources down at once (R33, R168, R258). Bites every time a source is added without the bump — it broke the whole nightly refresh twice.
- Run `tools/preflight_registry.py` before every registry commit, and write prose fields as `>-` block scalars — a bare `: ` inside a plain YAML scalar kills `registry.load()` for the entire fleet (R258, R168). Parse a machine-read file with its own production loader in the same breath as the edit; pytest doesn't load the registry, so green tests prove nothing here.
- Only `live:true` sources run in the daily CI; a flagged digest source shows LAST-RECORDED state, not a fresh failure — code fixes change nothing until the source re-runs (R23, R147). Bites when you diagnose "today's failures" that are week-old stored verdicts.
- Cadence is an input to the due-check, never a promotion filter — filtering out `static`/`irregular` hid 10 fetcher-ready sources (359,539 series) that stayed frozen after being "shipped" (R157). DONE for a source = catalogued + served + verified + ON A SCHEDULE (R158).
- `--source X` is a filter over the due set, not a force; a not-due source prints `0 unit(s) processed`, exits 0, and the green run proves nothing. Promotion proof = `force=true` + units>0 + rows counted (R50, R35). A `locked` unit (stale lease from a crashed run, held up to 1h) is another vacuous green — find positive evidence the fetcher's code executed (R193).
- Four things start runs: the live tier, the updater-heavy matrix, sec-edgar-daily, and `run_local_heavy.ps1` (which runs everything with `run_location: local` regardless of `live`) — any coverage counter that misses one publishes false numbers (R262). `run_location` is enforced only because `_wrong_location()` was added; a registry key nothing reads is a decision that was never implemented (R202).
- Firing several `workflow_dispatch` runs at one concurrency group silently cancels queued ones (queue depth = 1); serialise dispatches and read `conclusion`, never `status` — `completed` covers cancelled (R81). Re-enabling a workflow after its cron window skips that day; catch up as sequential single-day dispatches, never one multi-day job (>6h ceiling kills it) (R12).
- Never run a bare local `python -m updater.run` — it walks the full fleet including OOM-unsafe vdem, thrashes to ~99 GB, and holds the SQLite lease so later runs die `database is locked`. Local = always `--source X`; serialize local runs against CI's single-writer CAS state and skip the cron window (R39, R5).
- Bound the run INSIDE the system with headroom for teardown (state push, syncs) — the platform's 300-min kill loses even the successful sources' state (R66b). A cooperative budget checked between units truly bounds budget + the LONGEST single unit; require headroom > longest unit, and save rotation bookmarks per sub-unit because the 45-min cap kills before end-of-function saves (R286, R273).
- Isolate anything over ~10M rows into its own dispatch — serial sources accumulate memory peaks; exit 143/137 in a runner log means OOM-killed, not a code bug (R45). A run whose step conclusion is `cancelled` may be a destroyed runner; `gh run view --log-failed` returns EMPTY for cancelled steps — use `--log` (R187).

### Fetchers & tally semantics
- `tally.structural_unit()` is a WHOLE-SOURCE veto (`finalize()` raises DefinitiveError, nothing publishes). In a heterogeneous multi-file source count a zero-row file as `empty_unit()` and do NOT advance its vintage; reserve structural for a genuine whole-source break (R44). It silently zeroed owid/ons_uk/ember runs.
- Any fetcher that merges rows MUST report `series_cursors` or the run demotes to `partial` "no series_cursors" — and a `partial` never sets `last_success`, so the source re-fetches forever and its CSVs are never re-derived (R41, R174). Cap the ACCUMULATED cursor set (`CURSOR_CAP=50,000`, `merge_cursors()` across files) — an unbounded fold on ilostat (~30.8M series) or abs (376M) kills the runner (R175, R176, R188).
- A parser SELECTION/keying fix is a RE-GRAIN: `series_key` changes, old and new rows never collide, the file only grows and never-shrink can't see it — CLEAN RE-PULL (delete + re-ingest), never merge (R22, R27). Migrating the parser is HALF the job: the delta-query builder picks the tailed axis and must move in lockstep or the live delta silently freezes (R26).
- Many-request fetchers (boe/census/idb/noaa class) parallelize from the start at the INGESTER'S PROVEN worker count with thread-local Sessions, then merge serially (R40); the ceiling is the server's rate limit, not the request count — a 429 burst means lower concurrency, never more retries (R40b). The publisher's pacing constant is usually already in the module you're importing — read it before looping against the host (R132, R46).
- All store reads/writes go through `blob.*` — a raw `pq.read_table`/`open()`/`glob` on `config.source_dir` passes locally and silently ingests nothing under CI's `AQUEDUCT_BACKEND=r2`; a local run is structurally blind to this. The only acceptance test is a real `backend=r2` run showing rows ingested (R36, R3).
- Any bound (budget, cap, page limit) needs a persisted resume mechanism or it is a truncation — a fixed budget over a sorted listing re-works the same prefix forever, and the "they drain next tick" log line is a lie (R130, R190). Every early-exit path must report `partial`/transient and NOT advance the vintage, or the unfetched remainder is never pulled behind a green run (R172).
- Read the consumed function's actual `return` keys — `stats.get("rows") or stats.get("n_rows") or 0` defaulted to 0 and reported `no_change` on a 119,105-row publish, leaving CSVs underived (R186). A best-effort helper that returns `{}` on failure is indistinguishable from "nothing changed" — count what it produced on REAL store files, not on a fixture you authored (R206-helper: bls keys on `series_id`, not `series_key`).
- Vintage signals: a relay hash (DBnomics `indexed_at`) certifies the relay, not the publisher — it can prove staleness, never freshness (R73); a pinned-URL ETag misses whole new editions — watch the LISTING page, and treat an empty listing as structural (R78). Probe the validator before gating on it: a per-request-generated Last-Modified (fed_board) or CDN cache-fill time (whr) never matches, so the source re-downloads forever while looking cached (R164, R184); an Apache ETag's mtime half flaps across replicas — gate on Content-Length plus a MAX_AGE backstop (R165). A two-probe stability audit is blind to movers slower than the gap (TTL-period movers) — the audit needs a FETCH-TIME verdict (R184).
- Gate bulk pulls on VOLUME against what is already published — a well-formed, parseable 200 can carry 4.6% of the dataset and pass every parse-success guard (R83). Before merging a new upstream vintage, assert its keys LAND ON published ids (count the intersection) and refuse below a floor — an id-vocabulary fork adds new series beside frozen live ones and turns the health gate green over a dead source (R79, R91). For sources served by a dataset they were MERGED INTO (fao_qa/QCL), `restrict_to_published` — coverage is not containment; check what the rebuild ADDS as well as what it covers (R91, R82).
- A date tail extends the series the store HAS; merge only keys already in the store and report the skipped count — the store can be a legitimate subset of the API (R278). Before tailing incrementally, assert `distinct(dedup_keys) == rows` on the store alone; an under-keyed store makes the first merge collapse the file and fail never-shrink forever (R280, R177).
- `registry.yaml` strategy_reasons and adapter notes are HYPOTHESES from whoever surveyed the source — send the narrowing request and compare counts before building on a claimed capability (ipea's `$filter` is silently ignored; fed_board's promised ETag doesn't exist) (R160, R164). Build the probe URL from the downloader's own constant via one expression, never retype it (R162).
- Before wrapping an ingest as a fetcher, read how it DISCOVERS work: a hardcoded period list, pinned version, or fixed window is a staleness bomb with a scheduler attached (stats_nz frozen at Dec-2024) (R159). Most ingests are backfill-shaped (skip-if-present) — budget an extract-the-parser refactor per source, not a wrapper (K-note).
- DBnomics is BANNED (Ahmed's standing instruction): no fetching, probing, or citing its coverage; every source from its own publisher; the last WHO relays must migrate (R251). Sweep bans across every executable surface — ps1 watchdogs and audit tools count (R259).
- CI must be TOLD to install every import: a missing dep makes `fetcher_implemented()` return False and the source silently PENDING forever ("no adapter built") — `tools/audit_updater_deps.py` walks the import graph statically in preflight (R178). Cap dev/CI on the same pandas/pyarrow majors (R312-digest).
- Arrow's 2 GiB int32 string-offset limit: `group_by` on an over-2GiB string column KILLS the process uncatchably (0xC0000005/SIGABRT) — it is not an OOM and more RAM cannot fix it; dedup via sort on `large_string`, and fix EVERY `group_by` call site, not the one that crashed (R197, R207-arrow). A merge-peak measurement must exercise BOTH inputs (existing + new); measuring one side routed two sources to runners that died (R199).

### State & verification
- A `unit_state` dump is accumulated history, not a run result — it keeps rows for de-registered sources; reconcile against the registry and prefer the runner's own `N unit(s) processed` (R59). Age-since-success and age-since-attempt are different measurements; check a source RAN before diagnosing it (R246).
- "Scheduled" is not "attempted": the daily budget reaches ~20 of ~106 cloud sources, so a fetcher fixed today advertises yesterday's failure for days — compare the verdict's age to the last commit on the fetcher and force-run before diagnosing (R277, R246).
- A kill is a request; only a re-listing is an outcome — `Stop-Process`/`taskkill`/`pkill` all silently failed in one session and left duplicate derives competing on one prefix (R90). A process/log query can match ITSELF — exclude `$PID`, prefer exact script paths or a lockfile identity; a "target" whose PID changes every pass, or your own shell dying after the kill, means you matched yourself (R49, R260, R203).
- Liveness = OUTPUT ADVANCING (object/row counts between two checks), never recognition in a process table or a possibly block-buffered log; launch background jobs with `-u`, and READ THE JOB'S LOG before declaring it dead — an 8-second I/O sample on a 4-minute-cadence crawler kills healthy work (R54, R115, R62). Never pipe a watched job through `tail` — the pipe buffers until exit and a healthy job looks stalled (R53, R336-digest).
- A watchdog must run concurrently, be able to kill, and confirm its action's post-state before reporting success; put the deadline where the hang happens (every retry attempt), and state the honest bound including the in-flight request (R53, R63, R14). A heartbeat must be readable by someone who can act (published to R2, read by CI; absent = exit 1 UNINSTRUMENTED) — a heartbeat file on an unattended box has no reader (R274, R260).
- A cadence/"success" stamp is gated on the DURABLE artefact (push-state committed), not on reaching the end of the script — a crashed pass that lost its CAS still stamped success and stood the guard down 20 hours (R208-stamp).
- Never let a shell one-liner decide a push succeeded: verify `git fetch && git rev-list --count origin/main..HEAD` == 0 and check the claim against `git show origin/main:<file>` — grep-driven `||` logic reported five rejected commits as pushed (R42).
- Every probe needs a known-present CONTROL in the probe list, and a failed control VOIDS the run — a wrong field name, invented id, or wrong-repo read makes EVERY item read as absent (R52, R57, R93, R106, R134, R192). Before reporting any absence, print one whole record and read its keys; an error body coerced by `.get(...) or []` is indistinguishable from an empty result (R106, R134).
- Verify against the artefact users receive, with a check that would FAIL if your change were reverted — re-reading the column you just wrote can never fail (R103, R116, R119). When an end-to-end check contradicts your database read, believe the artefact (R116).
- Time arithmetic: parse timestamps explicitly to UTC and print the zone — PowerShell parses trailing-`Z` into local time, producing a 403-minute elapsed on a healthy 104-minute run, one sentence from a wrongful cancel (R198). An impossible derived number is evidence about your formula (R198).

### Serving pipeline (derive → catalog → D1 → worker)
- The catalog lives in TWO stores: D1 `econ-catalog` (Worker serving) and R2 `_aqueduct/catalog.db.zst` (updater's CSV-coherence reference). Every mutation must reach BOTH via `tools/refresh_r2_catalog.py` (superset-verified, backup-first) — a source in D1 but not R2 demotes every run to `partial` "coherence unmet", and that class silently froze ~650,000 series (R38, R271). The R2 refresh is classifier-blocked for Claude — ask Ahmed, don't retry (R250).
- Local `data/catalog.db` is gitignored and NOTHING serves from it; any claim about what users see comes from D1 or the served file, and the serving path reads `series.license_id`, not `source.license_id` (R96, R107, R116, R119). Two stores that can disagree must not share one diff/plan — make the plan the desired state and every writer idempotent (R107); use UPSERT wherever a new key can appear, and audit the population both directions (files↔rows, MISSING/ORPHANED) (R110).
- The serve path is raw parquet → catalog → per-series CSV derive → D1 + R2 `series/` → worker; a corrected raw parquet is invisible until catalogued, derived, and in the resolver — never claim user impact from the raw layer (R28). Ordering: derive CSVs, sync catalog/D1, THEN flip `SUPPORTED_SOURCES` — flag-first turns a 501 into a 404, a worse lie (M-20260727-09, R167). For retirements, commit+push the resolver removal BEFORE deleting data, or the next clean deploy resurrects the id over nothing (R155).
- `sync_state_d1.py` syncs freshness and NEVER the catalog — new series need `sync_catalog_d1.py` or they are hosted-but-invisible (31,259 stranded series; boe served 21 of 30,674) (R60). Measure completeness at the surface users touch, reconciling local vs R2 vs D1 (R60).
- `make_servable.py` and `catalog_complete.py` are PUBLISHING tools — check the verbatim licence before running them (`make_servable owid` would have published 1,048,968 DISPUTED-licence series; `catalog_complete cso` inserted 9.9M rows as a "print test") (R118, R150).
- Read the served BODY, not the status code: HTTP 200 tests delivery, not correctness — un-gated sources served with no Source/License/Terms lines, and an attribution check satisfied by a substring of the series id is not a check (R124, R194). After any un-gate or publish, read the citation header and confirm attribution/licence/terms (R124).
- After editing any list, grep the LITERAL token — a four-line comment saying `wid` was added compiled, deployed, and left the source searchable-but-undownloadable (R125); a heading over a query is a claim about that SQL, not the script (R143).
- A loop that PUTs to a key derived from the DATA silently overwrites when two iterations share the key — check `distinct(keys)` vs `count(keys)` before the first upload (92 cso tables would have served partial rows) (R133).
- `csv_derive failed N/M` on an r2 runner is a scratch-mirror artefact documented in `orchestrate.py` — the runner only holds files that run wrote; it is NOT a staleness count. Grep the repo for a failure string before theorising (R151, R147). "(over derive-all cap)" in the note is a hardcoded, untested cause — the count is the datum, the cause is a hypothesis (R152).
- A 501/404 seconds after `wrangler deploy` is usually edge propagation — retry and cross-check a second endpoint reading the same state before touching config (R138); a plain fetch can hit a stale edge copy, so an ABSENT marker is ambiguous — confirm on the deployment URL or cache-busted (R182-refined).
- econdatalibrary.com is a MANUAL Pages deploy (`npx wrangler pages deploy catalog/site --project-name=econdatalibrary`; Git Provider: No) — a git push publishes NOTHING; always check the live URL (R182).
- Worker and derive must share ONE key-encoding definition — `encodeURIComponent` vs Python `quote(safe="")` differ on `! ' ( ) *` (60,993 series 502'd) (R192); a commit message claiming "imported, cannot drift" is a claim about code — grep it (R191).
- Establish which bytes RUN before auditing/fixing production: the deployed worker builds from `D:\research\hf_wt_sso` branch `sso-build`, and FOUR worktrees declare `name = "hfdatalibrary-api"` — a deploy from a stale one removes the whole SSO surface; the DO-class refusal blocking it is a guard rail, not a config problem (R200 + addendum).

### R2 & blob I/O
- Every store LISTING goes through `blob.list_parquets` (`recursive=True` for nested stores) — `glob`/`os.listdir` under r2 return `[]` silently, and an empty listing is a legitimate value nothing objects to; `dst`'s `_total_rows` summed a scratch mirror and reported a 97.5% data loss that never happened (R261, R264). But check intent first: sources that list locally to `publish_file()` UPWARD are correct as-is (R261/R249).
- A store-routed sidecar needs BOTH ends checked — routing the read to blob fixes nothing if only the ingester ever wrote it, locally (cso's cursor was ephemeral every run) (R272). Read `_cursor_path()` instead of guessing filenames (R272).
- Measure the quantity the work would MOVE: an overwriting derive has a constant object count (use LastModified), while a stalled creator shows flat counts that ARE proof (R80, R85). Hoist any loop-invariant I/O call out of comprehension conditions — one listing per candidate id made 40,016 full R2 listings (R85).
- Do not poll a saturated service to watch a job you cannot hurry — repeated full prefix listings drew `ServiceUnavailable` and degraded the derives being measured (R140, R169). When something is slow, measure WHERE before adding workers — 16 threads on a full-scan-per-series algorithm did nothing; one sorted DuckDB pass did (R169, R88).
- Refresh a derived artefact and its SOURCE together, in the same block — CSVs on R2 built from parquets left local would be silently REVERTED by the next rebuild-from-R2; list the remote prefix for the layout you're writing first, and keep a `--force` path because a local-state skip cannot see remote drift (R108, R109).
- Never write to a store a background job of yours is still writing to — the re-export's part files restored the pre-fix value; and "no output where output was expected" is a failure signal, not a pass (R144, R131).

### Process & reporting
- Don't stop to report: a finding, success, or measurement is not a turn-ender; batch results into the next real milestone; the reserved list is only non-recrawlable deletion, DISPUTED un-gating, auth/billing, sending email as Ahmed (R43, R205-stop).
- One reported example = a class: enumerate mechanically (`grep -l` the exact defective line, execute the production code path across all callers), and the zero-result check DEFINES the work — memory-listed domains missed 40% of the PxWeb patch set (R256, R279, R95, R165). A reviewer's list of instances is a SAMPLE, not an inventory — enumerate the pattern across the file and paste the search output (R208).
- Every number in a claim needs a query behind it, at the grain the question is about — file-count vs country-count (3× error, R87), key-grain vs table-grain (96.4% inversion, R141), one-label-per-source aggregation (270× vs 70.5×, R98), sweep totals bucketed by cause (7.2B → 581M actionable, R111), `LIMIT 2` as a format census (R149), and a per-source ratio hiding three causes (R127).
- Substring tests on short identifiers or formatted sentences are not membership tests — `ppi` in "shipping", `imf_fsi` in `imf_fsire` (R2 prefixes need the encoded delimiter `%3A`), `cso` in "HCSO", `endswith("0 …")` matching 10/20/30 (R112, R129, R137, R142). Anchor on word boundaries, corroborate with a second key, and treat an order-of-magnitude swing between attempts as proof the instrument is wrong.
- Shell-generation hazards (each broke production output): quote heredoc delimiters (`<<'PY'` — unquoted executes backticks and eats `${...}`) (R92, R139); never regex-escape (`\b`,`\n`,`\r`) or backslash paths through a heredoc — bytes 0x08/0x0D land in the file invisibly (R181, R183, R203); `.ps1` files must be ASCII or BOM'd (BOM-less UTF-8 under PS 5.1 silently truncates execution) (R196); `PYTHONIOENCODING=utf-8` on every background job (em-dash kills cp1252) (R126); non-ASCII ids verified from Python `requests`, never bash-curl (false 404s) (R154).
- `cd` in a compound command retargets every relative path after it (ledger appends went into a PUBLIC repo — every ledger git command uses `git -C /d/research/hfdatalibrary`) (R135); a trailing `&` backgrounds the whole `&&` chain including the `cd` (R89); use the harness background flag XOR shell `&`, never both — the "completed" notification was about `echo` (R131); .NET file APIs ignore `Set-Location` — absolute paths always (R206-probe).
- Use the Edit tool, not scripted `str.replace` — replace-with-no-match returns the file unchanged with no error, and "wired" functions end up defined and never called (R109).
- Never run a write tool to observe its output — prefer read-only paths, disposable targets, `--dry-run` (R118). Never size/hash HTTP bodies through `$(...)` (strips trailing newlines) (R17).
- When a number surprises you, suspect the instrument first (one minute: known-good input, endpoint exists, WHICH store) — thirteen of one session's 25 entries were self-inflicted instrument errors at 20–40 min each (R123). A check must be shown able to FAIL — set the constant wrong, feed the degraded payload, run the discrimination test (R64, R142, R168).
- A security fix is verified by re-running the ATTACK through the patched code and naming the line that blocks it — flipping a flag nothing on the attack path reads closed nothing (R205-security). "Present on the page" ≠ "can run": verify the dependency RESOLVES where the code executes (`typeof window.EKD` — download.html never loaded the SDK) (R207).
- Open canonical docs before re-deriving (REDISTRIBUTION_COMPLIANCE.md, DATABASE_LICENSES_VERBATIM.md); a 404 on a guessed path is evidence about the guess (R7, R104). Findings go in this ledger, never new documents (R148); the ledger is append-only — insert at an anchor and verify the entry COUNT after writing a shared file (R247).
- A round number (100,000) in a response is a CAP, not data — completeness checks on a truncated response prove nothing; check the envelope count and diff against a narrower query (R201). A far-future date is a question, not a finding — projections are real (ABS 2061, bfs 2150); a defect is a sentinel or counter, and the bug may be in the CONSUMER (newest_obs vs frontier_obs) (R204, R267-digest).

## The Rules Digest verbatim summary (the numbered checks at the top, one line each)

1. Compute what the SYSTEM computes or read its output — don't re-implement its rule (business vs calendar days; `observed` vs `frontier` already separated in health.py) (R318, R327).
2. Read a long job's ARGV, not its progress, and never pipe it to `tail` — a dry run prints real-looking numbers, and a tail-buffered pipe makes a healthy job look stalled (R323, R336).
3. A sweep reports TWO numbers — found AND unreachable; "0 defects in 0 files examined" is not a result, and a hardcoded dead path is the commonest way to get one (R315, R330).
4. A probe reporting ABSENCE needs a known-PRESENT control IN the probe list, and a failed control VOIDS the run; never regex a language whose comments can contain the delimiter (R316, R329, R338).
5. A one-sided test on a two-sided failure yields a number that only LOOKS like a measurement (future-only date audit missed counter-as-year: 273,980 vs ~637,000) (R322).
6. Two writers, one store: state is a MERGE of separate lineages, not a freshness comparison — diff BOTH directions with counts before reconciling, and name WHICH database you hold (R340).
7. Re-running the same query is REPRODUCTION, not verification — check with a DIFFERENT instrument (parquet footer vs DuckDB re-scan), and say which quantity you actually established (R342).
8. Measure completeness by enumerating from the side that can be OVER-complete — a catalogue-drawn sample can't see uncatalogued store growth, and a net figure can cancel two opposite defects (R341).
9. A reserved task reserves what its TEXT says, not its prefix — and "the queue is empty" is a claim needing the same proof as any other; an invented category is a hypothesis to test against the system's list (R343).
10. Check your evidence POSTDATES the fix before calling the fix a failure — "still broken" and "never tried" look identical in a table of past runs (R339).
11. When a component has a fallback, plausible output proves NOTHING — prove the PRIMARY path returns the value, write/read through the SAME layer, or make the fallback announce itself (R344).
12. "Deployed" is a state of the RUNNING system, not the repo — find what turns a commit into a deployment; and a new check must be fed something that MUST fail, with the control verified negative (R345, R346).

Supplementary digest blocks: write-path lessons must be read back from where the READER stands, picking the sample most likely to fail (R328, R330, R332); most sources have TWO parsers (ingester + fetcher) and a fix in one is not shipped — and an axis-selection change is a re-grain (R333, R22); a flag naming a store must SET it — print the RESOLVED backend, never the flag (R335, R296); a future date is usually a projection, a defect is a sentinel/counter (R320, R322, R327); range tests cannot detect code-as-year fabrication — detect time-inside-series-identity structure and inspect what SURVIVED a repair (R334); `obs_count` means rows-this-run on productive runs and whole-store on quiet ones — count the store (R326); a "mis-selected" date axis is usually an unparseable one (a None-returning parser votes for every other column), and after a selection fix assert the table still yields ROWS (R331).
